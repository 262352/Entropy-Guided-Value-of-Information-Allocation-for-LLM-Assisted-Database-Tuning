# Twitter：新版 CogniTune 与官方 MCTuner 的 50 轮对比

本次实现名为 `cognitune_v3`，对应决策熵引导搜索适配的新设计。原有
`cognitune_v2` 和 TPC-C 的数据、脚本均保留。此文档不包含新的真实性能结论。

## 运行

在当前已配置机器上：

```bash
cd /root/OpAdviserPrivate/Entropy-Guided-Value-of-Information-Allocation-for-LLM-Assisted-Database-Tuning
bash scripts/run_twitter_compare.sh both
```

首次运行自动构建独立的测量版 BenchBase jar、加载 Twitter 模板，然后串行运行
两种方法。每种方法 **50 次评测总预算，包含 10 个相同的持久化 IID 初始配置**，
即 40 次自适应搜索。初始设计包含默认配置及九个 IID 抽样配置。共享的是配置，各方法独立实际测量初始点。
每种方法前 12 次评测有健康检查；任何失败即停止。

默认三次默认配置测量的 CV 超过 15%、或方法结束后的默认性能漂移超过 20%
会停止实验。如果需要继续已有约定的探索性诊断，可显式运行：

```bash
bash scripts/run_twitter_compare.sh both --allow-unstable-baseline
```

这个参数允许基线波动，不会跳过数据库基础设施错误或前 12 次评测失败。
高波动下的结果用于诊断，不能直接视为方法提升的证据。

也可以分开运行，但须串行，不能在同一实例同时运行：

```bash
bash scripts/run_twitter_compare.sh cognitune_v3
bash scripts/run_twitter_compare.sh mctuner_official
```

已有完整方法会跳过；部分调优轨迹默认不会被覆盖或自动重新执行。新版 CogniTune 可通过显式 `--resume` 续跑，见文末。
基线检查可复用兼容的成功测量，失败证据会保留。更换预算、代码协议或设置时
使用新的 `TWITTER_RUN_DIR`；不能把旧 TPC-C 推荐缓存复制到本实验。
运行结束后额外进行各三次最佳配置验证及三次默认配置漂移检查，均不计入 50 次预算。

只检查安装与连接、不加载数据、不调用 LLM：

```bash
PYTHONPATH=src .venv/bin/python scripts/compare_twitter.py check
```

## 工作负载与公平性

- PostgreSQL 14.9，端口 55432；独立数据库 `cognitune_twitter` 和
  `cognitune_twitter_template`，每次从同一模板恢复。
- 使用 **BenchBase 生成的 Twitter 数据和事务工作负载**，不是原始推特归档数据集。
  scale=10：5,000 用户、200,000 初始推文；关注图由标准加载器生成。
- 16 客户端，SERIALIZABLE；事务顺序为 GetTweet / GetTweetsFromFollowing /
  GetFollowers / GetUserTweets / InsertTweet，权重 `1/1/7/90/1`。
- 15 秒预热、60 秒测量；fsync、synchronous_commit、full_page_writes 始终开启。
- BenchBase 随附 trace 的 ID 超出生成表的主键范围，因此显式采用
  `(id-1) % table_size + 1` 映射。保存原始及映射后的 SHA256、行数与映射规则。
  此修改避免 GetTweet 大量访问不存在的行；它是实验协议的一部分。
- 两方法共用同一 60 参数合法域、LLM `deepseek-flash`、数据模板和评测器。
  MCTuner 使用官方提示词、旋钮排名、空间分解、UCT 和 GP/EI，保留已有适配：
  修复提示词括号格式化、路径、最大化接口；归一化坐标，离散参数按序数映射。
  这是官方核心适配版，并非完全未经修改的官方端到端环境。
- 新目标为 `Measured Goodput (requests/second)`：只统计开始和结束都位于同一
  MEASURE 阶段的成功请求，再除以测量秒数。预热成功和失败请求不计入分子。
  Worker 内以成功计数增量识别成功，因此重试后的最终成功不会重复记数。
  同时保留上游 Goodput / Throughput。新指标不能直接与旧 TPC-C 的 Goodput 数值混用。
- 补丁在 `scripts/build_measured_benchbase.py`；原始源码和 jar 保留，
  独立 jar 的哈希和上游提交写入协议。

## 新代码的闭环

1. 每轮基于联合 GP 后验，对单旋钮及已确认小组做有限探针审计。
   条件改善概率和区间决定 exploit / verify / pause 排序，保留核心参数、
   专家覆盖及等待年龄；每 8 个自适应步骤预留一次真实回访评测，计入预算。
   条件激活会带上父旋钮，硬资源约束按完整配置检查。
2. 四个专家每轮收到当前最优配置、近期测量、条件潜力和上轮区域，各返回结构化
   区域、稀疏补丁和联合假设。程序从区域连续采样，保留全域探索概率。
   数值中心每轮最多移动全局归一化域的 0.1；普通补丁最多改变四项、L1 距离不超过 1.5（布尔翻转的距离为 1）。
   扩围需真实的区域外改进证据；细化需有限内外探针对比和后验最优位置集中。
   跨领域假设需相关专家对同一合法补丁一致确认，单独标为 joint。
3. 每专家独立抽取相同数量审计候选（默认四个），与其生成配额无关；合法样本不足
   时统一降低审计规模，禁止重复填充。审计集、锚点和来源映射在观测前冻结。
   相同配置去重保留来源子集；joint 和 reference 是独立策略，不冒充专家共识。
4. qLogNEI 使用所有成功历史点作含噪基线。仅在
   `logNEI >= max(logNEI) + log(0.8)` 内，考虑对“最佳提议来源子集/无实质改进”
   的预计信息增益。使用相关潜变量抽样、带噪幻想条件化和共同随机数。
   默认短名单 16、幻想 16、后验样本 256，所有审计点均保留在参考集合。
5. 至少八个逐步预测残差且最近残差的 95% 区间覆盖率不低于 70%，才启用信息选择；
   估计信息增益须超过两倍外层 Monte Carlo 标准误，否则用 qLogNEI。
   最后一轮仅使用 qLogNEI，不为后续配额购买信息。
6. 观测后，在同一冻结审计集上更新来源概率，按来源子集均分机会质量，转为有最低
   配额和整数约束的下一轮候选预算。无收益证据时回到均匀分配。
   这是当前候选机会估计，不是未执行候选的真实收益或永久专家能力。

这是有限探针和有限审计集上的可计算近似，不是对连续搜索空间的精确熵积分。
校准门和信息估计误差都有日志，尚需真实实验检验其稳定性。
每轮四专家都调用 LLM，配额分配的是**候选配置数**，不能宣称减少每轮 API 请求数。

## 查看日志

- `runs/cognitune_v3/seed_0/round_diagnostics.jsonl`：proposal / outcome / joint_review。
  包含活动旋钮、改善概率与区间、专家原始建议、范围请求与实际变化、内外潜力、
  审计集、候选、qLogNEI、信息增益及标准误、校准状态、执行原因、后验来源概率、
  配额前后值与配额是否改变。
- `llm_cache/cognitune_v3/*.json`：每轮完整提示词、结构化结果、实际模型及 token usage。

- `protocol.json` / `profile.json`：指标、预算、共享初始设计哈希、模板和 jar 来源。

## MCTuner 推荐准备阶段的 JSON 重试

官方适配器会复用已有旋钮 `_final.json` 和成功 LLM 响应缓存。模型返回空响应、
截断 JSON、或 `finish_reason=length` 时，最多尝试三次，输出上限从 4096 逐步增至
8192、16384。重试仅要求完整 JSON，原始专家任务和评分规则保留。
成功响应的缓存键保持兼容；失败响应不会作为推荐使用。
每次收到的原始响应（包括 finish_reason、usage 和解析错误）先写入
`llm_cache/mctuner_official/attempts/<请求哈希>/`，方便判断是否输出超限。

若准备阶段失败且尚无调优轨迹，修复服务问题后重新执行原命令即可复用已有准备结果；
无需删除目录。调优已经开始后的部分轨迹仍遵循不自动覆盖、不重新运行的规则。


## 临时网络故障

两种方法共用的 DeepSeek 传输层对 SSL EOF、连接中断、读取不完整、超时，以及
HTTP 408/429/500/502/503/504 做有界重试。单次传输最多六次尝试，重试等待分别为
10、20、40、60、60 秒，终端会打印进度；每次尝试保留原有请求超时。
401/403 等密钥或权限错误立即停止。达到上限仍失败时，MCTuner 适配器在同一
`attempts/` 目录记录传输错误及尝试次数，不会再套一层网络重试或覆盖成功缓存。
这是连接故障恢复机制，无法保证上游服务持续不可用时实验仍能完成。


## 动态作用域校正与断点续跑

专家的 `previous_regions` 只提供本轮 `allowed_knobs` 对应的历史区域，中心用实际
参数单位，半宽仍用归一化单位。全局域及完整历史配置用于理解背景，不扩大当前写权限。
已知但已退出活动集的区域推荐会从可执行建议中移除，完整记录在 `interface_repairs`；
带越界旋钮的补丁整条延后，不截掉其中几项后改变其联合含义。
没有可执行 patch 的联合假设作为诊断保留；未知旋钮名或非法当前区域取值仍需模型纠正。
可选联合假设按下述规则逐条校验，拒绝其中不合规项。普通专家若没有留下任何可执行作用域内建议，也会重试。

对已经保存的 CogniTune 评测，可显式继续：

```bash
bash scripts/run_twitter_compare.sh both --resume
```

如先前使用了 `--allow-unstable-baseline`，续跑时保持该参数。
续跑会验证共享初始设计、空间、算法参数和两份评测轨迹的一致性，保留成功/失败记录，
不重复运行已经记录的数据库评测。每次完成后原子保存区域、等待年龄、配额、校准残差、
联合组和程序随机数状态。MCTuner 的部分轨迹目前仍不支持续跑。

旧版未写检查点的运行，可从每轮完整 proposal/outcome 诊断重建控制器；如果诊断不足
则停止，不猜测状态。**旧程序没有保存随机数状态，因此首次旧轨迹恢复会开启并记录一个
确定性的恢复随机流，不能称为原随机流的精确重放。** 已测数据保持不变，后续中断使用
新检查点恢复随机数状态。恢复方式会写入 `round_diagnostics.jsonl` 的 resume 事件。


### 联合建议采用逐条校验

模型可能把一个联合补丁写成 `[{"a":1},{"b":2}]`。接口在没有取值冲突时合并为
`{"a":1,"b":2}`，不更改推荐值；只有提供精确取值映射时才允许把 `knobs` 字段
作为 `patch` 别名。仅列出旋钮名称时不推断推荐值。

同一旋钮存在冲突、超过四项、未知名称、非法取值或其他不可执行格式时，整条可选
联合建议被拒绝并记录原文及原因，不拆成部分补丁，也不拖停其余合规区域/候选。
保留下来的联合建议仍须通过相关专家同意及完整配置约束。所有归一化、拒绝记录都在
`interface_repairs` 中；若整个回复没有可执行内容，仍会要求重新生成。
